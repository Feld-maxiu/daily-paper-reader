## 摘要
LLM 智能体越来越多地承担长时间运行的任务，其历史记录远超单个模型上下文窗口的容量。现有方法将早期交互压缩或提取选定信息为固定记忆表示，在知晓未来需求之前就决定了要保留什么。我们提出 Scroll，一个将每次智能体会话视为可执行“会话环境”的上下文管理器。该环境由一个仅追加的事件日志和一个沙箱化的持久 Python 内核支撑。内核在多次模型调用之间维护一个带类型的命名空间，使工具输出、检索到的历史记录以及派生状态可以绑定到变量，而不是在每次调用时序列化到提示中。模型编写的代码通过 exec 搜索、物化和转换会话状态；只有被显式打印的投影会进入模型下一次调用的工作视图。因此，上下文管理变成一项编程任务，继承了 LLM 日益提升的编码能力，而事件日志则保留了无损的历史真实记录。当工作视图接近其预算时，较早的片段会被逐出但仍可恢复：逐出索引保留与事件日志确切地址相关联的紧凑地标，使智能体可以直接导航到被逐出的区域，而无需搜索整个日志。以 Qwen3.8-Max 为骨干模型，Scroll 在 LongMemEval_S 上达到 94.8%；在 BEAM_10M 上达到 73.1%，比已发表的最佳记忆系统高出 5.1 个百分点；在 LOCA_256K 上达到 86.7%，比已发表的最佳长时程智能体高出 37.4 个百分点。

## Abstract
LLM agents increasingly take on long-running tasks whose history grows far beyond a single model context window. Existing approaches compress earlier interactions or extract selected information into fixed memory representations, committing to what to preserve before future needs are known. We present Scroll, a context manager that treats each agent session as an executable Session Environment. The environment is backed by an append-only Event Log and a sandboxed, persistent Python kernel. The kernel maintains a typed namespace across model calls, allowing tool outputs, retrieved history, and derived state to be bound to variables rather than serialized into the prompt at each call. Model-written code searches, materializes, and transforms session state through exec; only explicitly printed projections enter the model's working view for the next call. Context management thus becomes a programming task that inherits the improving coding abilities of LLMs, while the Event Log preserves lossless historical ground truth. As the working view approaches its budget, stale spans are evicted but remain recoverable: an eviction index keeps compact landmarks tied to exact Event Log addresses, so that the agent navigates directly to evicted regions instead of searching the full log. With Qwen3.8-Max as the backbone, Scroll achieves 94.8% on LongMemEval_S; 73.1% on BEAM_10M, surpassing the best published memory system by 5.1 points; and 86.7% on LOCA_256K, exceeding the best published long-horizon agent by 37.4 points.

## 1. 论文的核心问题与整体含义（研究动机和背景）

- **核心问题**：LLM 智能体在执行长时程任务（如仓库级软件工程、深度研究等）时，会话历史持续增长，远远超过单模型上下文窗口的容量；更严重的是，模型能够可靠利用的“有效上下文”远小于其名义窗口。
- **现有方法的局限**：
  - **上下文压缩**：截断、丢弃工具输出、将较早轨迹替换为摘要。这类方法在观测时点就决定了哪些信息存活，未来可能需要的信息可能被永久丢弃。
  - **外部记忆**：在摄入时抽取事实、片段到独立存储，之后通过检索接口读取。同样在知晓未来需求之前就固定了“保存什么、如何检索”。
  - 两种方法本质上都是有损的：模型只能通过摘要或记忆库看到历史，任何未被保留的细节即使原始日志仍存在磁盘上也无法触达。
- **整体含义**：长时程任务往往需要精确的历史证据或对过去事件进行非平凡计算（例如比较相隔很远的工具输出），而“哪些信息将来需要”和“需要什么操作”无法预知。因此，论文提出 **Scroll**，将会话历史视为一个可执行的 **Session Environment**，把上下文管理从“提前压缩/抽取”转变为 **查询时由模型编写的程序**，从而保留无损历史并按需构造工作视图。

## 2. 论文提出的方法论

### 2.1 问题形式化

- 会话状态定义为：
  \[
  S_t = (L_t, P_t, V_t)
  \]
  - \(L_t\)：事件序列（含元数据）；
  - \(P_t\)：事件引用的 payload（原始内容，如完整工具输出）；
  - \(V_t\)：辅助派生状态（在 Scroll 中是变量命名空间；在其他系统中是记忆存储或摘要缓冲）。
- 每次模型调用消耗一个工作视图 \(c_t\)，满足 \(|c_t| \le C\)（\(C\) 为模型名义上下文窗口）。
- 上下文管理问题就是选择下一步视图的映射：\(S_t \mapsto c_{t+1}\)。
- **Scroll 的核心差异**：
  - 压缩方法：\(c_{t+1} = \phi(c_t, e_t)\)，在轨迹增长时即时应用有损算子。
  - 外部记忆：\(V_t = \psi(V_{t-1}, e_t)\)，在摄入时执行抽取。
  - Scroll：**将选择推迟到查询时**。完整状态 \(S_t\) 无损地持久化在上下文之外，映射 \(S_t \mapsto c_{t+1}\) 是一个由模型在步骤 \(t\) 编写的程序 \(\pi_t\)。该程序在 \(S_t\) 上执行、更新 \(V_t\)，并输出一个有界观察作为下一次调用。

### 2.2 持久会话环境

Scroll 将 \(S_t\) 实现为三个组件：

- **追加事件日志（Event Log）** \(L_t\)：
  - 跨会话边界的单一追加日志，是持久、无损的真实记录。
  - 每个交互追加一个带类型的事件，包含角色、会话/智能体 ID、时间戳、工具状态等元数据，并获得不可变、单调递增的 `seq` 地址。
  - 使用 SQLite 存储；默认检索采用 BM25 全文搜索（确定性，不需要索引时模型调用）。
- **持久存储（Durable storage）** \(P_t\)：
  - 小 payload 内联在 SQLite 行中；大 payload 外移到 JSON 或 artifact 文件，行内保留有界预览和恢复指针。
  - 外化 payload 通过惰性句柄（`ToolResultRef`、`ArtifactRef`）访问。
- **持久运行时与驻留命名空间** \(V_t\)：
  - 沙箱化 Python 内核跨模型调用持久存在；命名空间保存环境对象（驻留 Python 值、惰性句柄），每个对象携带类型、大小和来源元数据。
  - 工具调用返回 Python 对象，后续程序可直接操作。
  - 每次调用前，harness 向模型展示命名空间摘要：变量名、类型、形状，小标量值内联显示。
  - 内核对事件日志只读；数据库、文件系统、网络和工具访问仅限 harness 显式声明的能力。

### 2.3 程序化上下文构造

- 采用 CodeAct 风格接口，通过受控能力对象 `ms` 暴露四个操作（Table 1）：

| 操作 | 接口 | 作用 |
|---|---|---|
| LOCATE | `ms.search(query, k, ...)` | BM25 全文搜索 + 结构化过滤，返回候选记录及其稳定 `seq` 地址 |
| MATERIALIZE | `ms.expand(seq)` 或 `ms.expand(seq_lo, seq_hi)` | 恢复精确轮次或序列跨度，并加载惰性句柄背后的外化 payload |
| COMPUTE | 普通 Python + 数据库/文件系统/工具接口 | 过滤、连接、聚合、更新解析、检查工件、构造派生状态 |
| EXPOSE | `print(value)` | 将选定投影作为有界观察返回；其他一切留在内核中 |

- **执行模型**：模型通过 `exec` 编写代码搜索、物化和转换会话状态；只有显式 `print` 的输出进入下一次模型上下文。工具结果、检索记录和中间计算留在内核命名空间中，不逐轮序列化到提示。
- 示例：一次机票/路线规划中，模型把完整工具结果绑定到 `flights`、`routes` 变量，只打印前几行；需要历史偏好时用 `ms.search` 定位、`ms.expand` 恢复原文，在内核中过滤后打印最终结果。

### 2.4 可恢复的上下文逐出与离线导航

- 当工作视图超过预算 \(\rho C\) 时触发逐出过程（Algorithm 1）：
  1. 将 live turns 持久化到事件日志；
  2. 保护 active turn、近期尾部、最新工具结果；
  3. 将其余部分中的完整工具 payload 折叠为 `seq` 指针；
  4. 若仍超预算，按恢复成本递增顺序逐出最旧的已完成 span；
  5. 被逐出的 span 保留在事件日志中，其 headline 进入逐出索引。
- **Headline 地标**：在每次响应中，模型写一个简短 headline（任务、已验证状态、下一步、状态），与 `seq` 绑定形成地址到 headline 的映射 \(H\)。
- **分层索引**：每层最多 \(k\) 个块；当层满时，最新块保留完整细节，旧的 \(k-1\) 块合并成一行进入下一层。经过 \(n\) 次逐出后，索引占用 \(O(k \log_k n)\) 个块，对近期历史提供细粒度锚点，对远期历史提供粗粒度范围，每个锚点都指向精确的 `seq` 范围。
