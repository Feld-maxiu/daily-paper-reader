## 摘要
语言模型正从生成答案转向在交互式环境中追求长期目标。对这些智能体进行后训练需要长且异构的轨迹，而同步系统在 rollout 和验证完成之前会让学习器引擎空闲。为了挤出这些流水线气泡，异步训练会在不同更新之间重叠 rollout 与学习，但代价是策略滞后。我们提出 ThunderSyncRL，它在所有所需输入一经确定时就开始梯度计算，且不产生策略滞后。对于分组相对策略优化（GRPO），ThunderSyncRL 在某个轨迹的奖励一到达就计算该轨迹的得分梯度，而无需等待整组。对于在线策略蒸馏（OPD），它在沙箱中执行工具调用的同时，为每个已完成的智能体轮次中由教师评分的动作计算梯度。我们证明，梯度流式计算能产生与批量同步训练相同的 GRPO 和 OPD 更新，且不改变任一目标。在 SWE-bench Verified 和 Terminal Bench 4.0 上，我们训练模型达到相同性能，速度比同步训练最多快 1.9 倍。由于策略滞后为零，ThunderSyncRL 在固定预算下还比异步训练最多高出 2.47 个百分点。

## Abstract
Language models are moving beyond generating answers to pursuing long-horizon goals in interactive environments. Post-training these agents requires long, heterogeneous trajectories, and synchronous systems leave learner engines idle until rollout and verification finish. To squeeze out these pipeline bubbles, asynchronous training overlaps rollout and learning across updates, but comes at the cost of policy staleness. We introduce ThunderSyncRL, which starts gradient computation as soon as all required inputs are fixed, without policy staleness. For group relative policy optimization (GRPO), ThunderSyncRL computes each trajectory's score gradient as soon as the reward for that trajectory arrives, without waiting for the group. For on-policy distillation (OPD), it computes gradients for each completed agentic turn's teacher-scored actions while tool calls run in the sandbox. We prove that gradient streaming produces the same GRPO and OPD updates as batch-synchronous training, without changing either objective. On SWE-bench Verified and Terminal Bench 4.0, we train models to the same performance up to $1.9 \times$ faster than synchronous training. With zero policy staleness, ThunderSyncRL also outperforms asynchronous training at a fixed budget by up to $2.47$ percentage points.

## 1. 论文的核心问题与整体含义

- **研究背景**：语言模型正在从单轮问答走向长时程、交互式的智能体任务（如软件工程、终端操作）。这类智能体的后训练依赖大量长且执行时间高度异构的轨迹。
- **核心矛盾**：
  - 传统**同步训练（Sync）**在 rollout、环境交互和验证完成之前，让学习器 GPU 空闲，形成“流水线气泡”。论文实测同步 GRPO/OPD 中学习器空闲时间占步骤时间 **49.5%**；相关研究曾报告最高 **81%**。
  - **异步训练（Async / Fully Async）**虽然能重叠 rollout 与学习，但会引入策略滞后（policy staleness），即部分轨迹来自旧策略，可能需要重要性修正、裁剪或显式滞后控制，且会牺牲一定性能。
- **论文核心目标**：提出 **ThunderSyncRL**，实现“异步执行、同步更新”：学习器一旦拿到某个梯度源所需的数学输入，就立即开始计算，但整个 update 仍保持单个同步 optimizer step、固定策略快照和**零策略滞后**。

## 2. 论文提出的方法论

### 2.1 核心思想：依赖感知的梯度流式调度

- ThunderSyncRL 的核心原则是：**每当某个“objective source”的所有数学依赖固定，就立即释放对应的学习器计算**，而不是等待整个 group 或整个 batch。
- 它通过以下方式同时实现流水线重叠与零策略滞后：
  - 所有 rollout 和梯度计算都绑定在一轮更新使用的固定策略 $\pi_{\theta_k}$ 上。
  - 在逻辑 batch 关闭、所有梯度和工作完成后，才进行一次 optimizer step 并发布 $\theta_{k+1}$。
  - 发布后等待所有 rollout replica 重新加载参数、清理缓存并确认，才开启下一轮更新。

### 2.2 GRPO 的流式梯度分解

- 传统 GRPO 中，一个轨迹的 advantage 需要整组奖励的均值 $\mu_G$ 和标准差 $\sigma_G$，因此看起来必须等整组完成。
- 论文将组梯度写为：
  \[
  g_G = \frac{1}{m}\cdot\frac{G^{(1)}_G - \mu_G G^{(2)}_G}{\sigma_G+\epsilon}
  \]
- 其中：
  \[
  G^{(1)}_G=\sum_{i\in G}r_i H_i,\quad G^{(2)}_G=\sum_{i\in G}H_i
  \]
- $H_i=\nabla_\theta S_i(\theta)|_{\theta=\theta_k}$ 是第 $i$ 条轨迹的得分梯度。
- **关键做法**：只要一条轨迹自己的奖励和 token 序列到齐，就立即反向计算 $H_i$，并增量累加到 $G^{(1)}_G$ 和 $G^{(2)}_G$。当整组奖励到齐后再组合出 $g_G$。
- 因此，轨迹级 backward 不再依赖组内其他轨迹，但最终 update 与同步 GRPO 数学等价。

### 2.3 OPD 的 turn 级流式梯度

- 每个智能体轮次（turn）中，一旦冻结教师模型对学生的 action tokens 完成打分，就立即释放该 turn 的学生端 backward。
- 这样做可以让学习工具调用执行和后续轮次的同时进行。
- turn 级 token advantage 只依赖采样 token、因果上下文、固定学生和固定教师策略，因此满足零滞后的依赖条件。
- batch 最终的 token 总数 $N_k$ 要等 batch 关闭才能确定，所以 ThunderSyncRL 只推迟标量归一化，而 turn-level 反向计算提前进行。

### 2.4 框架流程

论文给出统一算法流程：

1. 固定 $\theta_k$，注册 batch 中所有 trajectories 和 groups。
2. 并行的 rollout/supervision 线程持续产出 ready sources。
3. 学习器线程按 readiness 顺序消费：
   - GRPO：轨迹奖励到达 → 计算 $H_i$ → 更新组统计。
   - OPD：turn 教师分数到达 → 计算 turn 梯度 → 累加。
4. batch 关闭后，完成最终 distributed reduction、clipping，并执行**一次 optimizer step**。
5. 发布 $\theta_{k+1}$，等待所有 replica 确认。

- **端到端无损加速**：
  - ThunderSyncRL 达到与 Sync checkpoint 相同 pass@3 所需训练成本降低：

- **零策略滞后下的性能优势**：
  - 在 128 GPU-hours 固定预算下，ThunderSyncRL 相较 Async / Fully Async 有更高 pass@3：
    - SWE-bench Verified：GRPO 最多高 **2.47 个百分点**，OPD 高 **1.27 个百分点**。
    - Terminal Bench 4.0：GRPO 高 **1.52 个百分点**，OPD 高 **2.02 个百分点**。
- **步骤墙钟时间缩短**：
  - GRPO：从 Sync 的 1,313.6 秒降到 ThunderSyncRL 的 687.7 秒，speedup **1.91×**。
  - OPD：从 1,330.3 秒降到 685.7 秒，speedup **1.94×**。
- **数学等价性成立**：
  - FP32 下梯度几乎完全一致，相对误差约 $10^{-6}$ 级别。
  - BF16 下两种 schedule 都与 FP32 参考接近，且参数更新路径与 Sync 收敛到同一曲线。
- **缩放理论**：
  - 当 rollout 与 learner 时间接近、尾部学习器工作与发布开销可忽略时，理想 speedup 接近 **2×**。
  - 实际 speedup 受阶段平衡、轨迹异质性、batch size、horizon 和后缀开销影响。

## 7. 优点

- **核心创新清晰**：提出“异步执行 + 同步更新”的梯度流式调度，消除了传统异步训练中的策略滞后问题。
- **数学保证明确**：
  - GRPO 的梯度分解和 OPD 的 turn 级 flowing 均有严格推导，并通过数值实验验证与同步更新等价。
- **工程实现完整**：
  - 给出算法伪代码、依赖释放规则、减少内存开销的 host 存储策略、零滞后发布机制。
- **实验公平性强**：
  - 在多个 objective、模型、硬件、LoRA/full fine-tuning 设置下与 Sync、Async、Fully Async 对齐对比。
  - 基准分离、checkpoint 选择、seed 处理、成本口径等都有详细说明。
- **对实践有价值**：
  - 在不改变损失函数、优化器、模型的前提下，直接把同步系统训练提升约 1.6–1.9 倍，并且不牺牲 final performance。

## 8. 不足与局限

- **加速效果依赖工作负载平衡**：
  - 当 rollout 或 learner 某一阶段占主导时，speedup 会下降，无法接近 2×。
  - 论文也承认：若 rollout 时间远大于 learner，或 batch 很小导致尾部学习器工作占比高，加速有限。
- **内存开销增加**：
  - ThunderSyncRL 需要保存 partial gradient state、GRPO group statistics、deferred context 等，峰值 GPU 显存高于 Sync：
    - 例如 Qwen GRPO 峰值从 Sync 的 117.0 GB 增加到 ThunderSyncRL 的 122.8 GB。
  - 对更大模型或多任务内存敏感场景可能造成压力。
- **扩展性尚未完全覆盖**：
  - 实验主要在 8 GPU 单节点上进行；多节点、更大规模 agentic RL 的扩展性还没有实证。
  - 其他目标函数、critic/PPO 类算法是否适用尚不明确。
- **异步 baseline 范围有限**：
  - Async / Fully Async 的具体方式跟随选定框架与特定滞后控制，不能代表所有异步 RL 系统。
- **基准和数据限制**：
  - Terminal Bench 4.0 仅 66 个任务，pass@3 等指标可能方差较大。
