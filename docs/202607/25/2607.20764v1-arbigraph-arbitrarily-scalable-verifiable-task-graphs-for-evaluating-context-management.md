## 摘要
我们提出 ARBIGRAPH，一个基准生成器，用于评估工具辅助的语言代理能否在扩展的推理工作流中保留、更新、组合和舍弃与任务相关的上下文。ARBIGRAPH 将每个任务表示为一个带有可执行 Python 求解器的自然语言问题，并通过类型化的中间状态（此处实例化为标量和列表值）组合任务。这种设计使得任务图的长度、依赖结构、干扰项数量和值类型均可控制，同时保持精确的自动验证。我们用数学题、GSM 风格的应用题和 Python 追踪任务类别实例化 ARBIGRAPH，并评估了一个 Qwen3.5-27B 工具辅助代理在四种拓扑结构上的表现。结果显示，在孤立任务上准确率很高，但在更复杂的依赖任务上显著下降：在分支依赖链的数学任务中，准确率下降了多达 33.3%。这表明 ARBIGRAPH 暴露了单任务评估无法发现的失败。我们的代码、生成的数据集和评估结果可在 https://github.com/pavelgolikov/ArbiGraph.git 获取。

## Abstract
We introduce ARBIGRAPH, a benchmark generator for evaluating whether tool-assisted language agents can retain, update, compose, and discard task-relevant context across extended reasoning workflows. ARBIGRAPH represents each task as a natural-language problem with an executable Python solver, and composes tasks through typed intermediate states, instantiated here as scalar and list values. This design enables controllable task graphs whose length, dependency structure, distractor count, and value type can be varied while preserving exact automatic verification. We instantiate ARBIGRAPH with math, GSM-style word-problems, and Python-tracing task categories, and evaluate a Qwen3.5-27B tool-assisted agent across four topologies. The results show high accuracy on isolated tasks but substantial degradation on more complex dependent tasks: accuracy drops by up to 33.3% on branching chains of dependent math tasks. This shows that ARBIGRAPH exposes failures that are not visible from single-task evaluation alone. Our code, generated datasets, and evaluation results are available at https://github.com/pavelgolikov/ArbiGraph.git

- **整体含义**：提出 ArbiGraph 基准生成器，将上下文建模为**类型化的计算状态**，通过可控制的任务图显式考察代理在依赖、干扰、分支等拓扑下的上下文管理能力，从而暴露出单任务评估无法发现的故障。

## 2. 方法论

- **核心思想**：将一组参数化的自然语言任务组成一个可验证的数据流图。图中的节点是任务模板，边表示数据依赖。整个图被渲染为单个提示，代理须根据依赖关系依次求解，最终答案通过可执行求解器自动验证。
- **关键技术细节**：
  - **任务节点**：每个节点包含输入、预处理适配器、自然语言提示、后处理适配器、输出和可执行求解器。输入/输出采用标量和数值列表两种类型，便于生成、组合与精确评分。
  - **任务组成**：根据输出‑输入类型兼容性构建有向无环图（DAG）。依赖关系显式命名前序任务的输出变量，但不透露答案值。
  - **适配器层**：预处理/后处理适配器负责在基准的通用标量/列表空间与具体任务参数之间转换，控制中间值规模（如列表长度≤10，标量绝对值≤100），防止复杂度爆炸。
  - **任务类别**：实例化了三类可执行任务模板：
    - **数学任务**：40 种手工选取的算子，涵盖线性代数、多项式、组合数学、几何等，覆盖所有四种标量/列表的输入‑输出组合。
    - **Python 追踪任务**：来自 LeetCode 数据集的 80 个算法函数，要求代理追踪具体输入下的执行结果，而非编写代码。
    - **GSM‑风格应用任务**：基于 GSM‑Symbolic 的标量到标量算术文字题，用于增加自然语言多样性。
  - **评估拓扑**：使用四种拓扑测量上下文管理：
    - **基线 (Baseline)**：单个目标任务，无前后文。
    - **遗忘 (Forgetting)**：目标前放置三个无关干扰任务，要求代理忽略无关计算。
    - **链式 (Chain)**：三个任务的线性依赖，最终目标依赖前序输出。
    - **多链式 (Multichain)**：分支图，中间状态分裂、独立演化后汇合，再进入最终目标。
- **度量与修复**：主要指标为最终任务准确率。采用带有计算器工具的代理，多轮交互。为减少格式错误、截断等机械失败，设计了工具调用修复、输出修复和截断修复的协议，只保障可评分，不干扰上下文管理信号。

## 7. 优点

- **创新的问题形式化**：将上下文管理抽象为类型化任务图中的状态传播、选择性遗忘和组合，与一般长上下文检索明确区分。
- **高度可控与可扩展的基准生成**：用户可自定义图拓扑、长度、干扰项、数据类型，自动生成可验证实例，支持精细化的压力测试。
- **多类别任务覆盖**：融合数学、代码追踪和自然语言算术，能揭示跨领域的上下文管理能力差异。
- **分离局部推理与上下文管理故障**：通过基线比较和拓扑间差值，清晰量化上下文管理特有缺陷。
- **修复协议设计严谨**：尽可能剔除格式错误、截断等机械失败，使评分聚焦于真正的上下文管理能力。

## 8. 不足与局限

- **模型覆盖有限**：仅评估了 Qwen3.5‑27B 一个模型，未比较模型家族、不同规模的代理或不同工具集成策略。
- **任务类型仍受限**：当前仅支持标量和列表值的合成任务，尚未扩展到图像、视频等多模态或更复杂的外部状态（如文件系统、数据库）。
- **拓扑尚简**：评估仅使用了四条基础拓扑，未探索更复杂的循环、大规模图或动态变化的依赖关系。
- **现实工作流代表性不足**：任务图目前为合成变换的线性或分支组合，与真实世界代理工作流（如浏览、多步检索、与用户交互）的结构仍有距离。
- **修复协议可能掩盖部分困难**：虽然修复关注意外格式问题，但多次修复请求可能间接提供额外提示，对真正的上下文管理能力测量造成微弱干扰。
- **评估规模**：虽然实验次数较多，但每个目标任务仅 16 个样本，置信区间尚宽，更大规模生成可进一步提升统计可靠性。
